# E2.1 — Repository Identity & Authentication Design

> Status: Design baseline only. No E2 product code, migration, configuration
> change, credential migration, commit, push, or deployment is part of E2.1.

## Decision driver

Today an agent obtains `RESTIC_REPO` and `RESTIC_PASSWORD` from its process
environment. There is no repository identity per purpose. Consequently, a
compromised backup agent can hold all material available to its configured
restic invocation; it is not a repository custodian boundary.

**Security invariant for E2:** a normal backup agent, using its regular backup
credential, must not be able to perform repository-wide destructive operations
such as forget, prune, or repository deletion.

`RESTIC_PASSWORD`, transport/backend authentication, and authorization are
different security layers:

| Layer | Purpose | Example | Must not be conflated with |
|---|---|---|---|
| Encryption credential | Derives access to encrypted restic data | restic repository password | Backend identity or permissions |
| Backend credential | Authenticates to storage/transport | rest-server Basic Auth, S3 access key, OS account | Encryption key |
| Authorization capability | Backend-enforced allowed actions | `PutObject` without `DeleteObject`, append-only endpoint | A UI field or a role name |

Possession of a restic password alone is not an authorization model. Conversely,
backend write permissions alone must not be presented as proof that a caller can
decrypt a repository.

## Current state

### FACT — in-source repository model and callers

- A repository has unvalidated free-text `type` and `location`, plus
  `encryption_mode`, `object_lock_enabled`, and `immutable_mode`.
- `encryption_mode` and `immutable_mode` are operator declarations. The latter
  is explicitly documented as not automatically verified against storage.
- Agent configuration contains one `ResticPassword` and one fallback `ResticRepo`.
  No repository credential is persisted in the catalog.
- Agent bearer tokens authenticate the agent to the control plane, not to a
  repository backend. They do not create a least-privilege storage identity.
- The repository API stores no backend credential and no credential reference.
- UI badges and the health score treat non-empty encryption and protected
  immutable-mode declarations as positive signals. These are not backend proofs.

### FACT — currently occurring or explicitly intended backends

| Backend family | Evidence in the repository | Current OSB support status |
|---|---|---|
| Local filesystem / mounted NAS | Installer and setup examples accept paths and mounted shares | Generic restic location; no capability discovery |
| S3-compatible storage (S3 / MinIO) | Agent/setup examples accept `s3:` repository locations; model mentions Object Lock | Generic restic location; no S3 API integration |
| rest-server / REST backend | Architecture and immutable-mode text mention `rest-server` / `append_only` | No rest-server deployment or configuration in product source |

No other backend receives an E2.1 design commitment. `type` being free text is
not evidence that a backend is supported.

### GAP / RISK

- No technical verification of repository authentication, TLS, append-only,
  Object Lock, WORM, authorization, credential separation, rotation, or drift.
- No offsite-copy relationship or second-failure-domain model.
- No managed retention executor is present in the agent poller, despite retention
  policy/schedule metadata and control-plane validation.
- Machine/process environment variables are a legacy compatibility path, not a
  managed secret store. In particular, current Windows installation persists
  `RESTIC_PASSWORD` as a machine environment variable.
- A repository-specific health endpoint currently cannot provide a reliable
  snapshot aggregate; it is not a repository security verifier.

## Backend capability analysis

The following is a capability boundary, not a claim that an operator has enabled
any option in a real deployment.

| Backend | Authentication / credential types | Can separate identities? | Write / read / delete boundary | Append-only / immutability | TLS | Rotation | E2 conclusion |
|---|---|---|---|---|---|---|---|
| rest-server | Basic Auth via `.htpasswd`; proxy-auth identity is also supported | Partially. Separate users can authenticate, but append-only is server-wide for an endpoint; a distinct custodial management path must be designed and proven | Authentication alone does not encode write/read/delete roles | `--append-only` blocks modification/deletion of existing backups; server configuration is the enforcement point | Native TLS with cert/key and minimum version setting | Replace/disable backend user; prove old credential denial | Strong E2.4 candidate, but only when OSB can interrogate the actual server configuration and validate an unprivileged destructive attempt is denied |
| S3 / MinIO | Access key/secret, temporary credentials, IAM/policy-backed identities | Yes, through distinct policies/principals | IAM/S3 policy actions can distinguish list/get/put/delete and lock inspection/configuration | Object Lock/WORM can protect object versions; governance bypass is a separate high-risk permission; only backend evidence is valid | HTTPS endpoint plus certificate validation; S3-compatible details vary | IAM access-key rotation or temporary credentials; prove old key denial | Best target for separate backup, restore, retention, and custodian identities, subject to restic's required API action set |
| Local filesystem / NAS mount | OS user/service account, mount credentials, filesystem ACLs | Only where the filesystem/server ACL model supports distinct principals; local path alone does not | File permissions can restrict actions but are hard to prove portably; a mounted share can collapse identities at the client | No portable append-only or immutable guarantee; NAS WORM is vendor-specific | Depends on SMB/NFS/server transport, not on restic location | OS account/password/key rotation; mount/session re-establishment | Treat as LEGACY/DECLARED until a backend-specific verifier exists; do not label immutable from a path or UI choice |

### Backend constraints that shape the model

- A restic backup needs more than an abstract `Put`: it needs the backend action
  set required by restic for repository listing, reads, writes, locks and pack
  management. E2 must derive and integration-test the exact minimal policy per
  backend/restic version before calling it `BACKUP_WRITE`.
- `RESTORE_READ` may be technically useful for a restore-only identity, but a
  restic repository password can expose repository contents. It is therefore a
  distinct **backend capability**, not a promise of confidentiality separation.
- `RETENTION` is destructive by design. It belongs on a trusted retention runner
  or custodian path, never on a standard backup agent.
- `REPOSITORY_ADMIN` is for creating/changing backend policy, Object Lock,
  users, certificates, or endpoint configuration. It must never be distributed
  to agents or exposed through regular repository APIs.

## Canonical target model

The future model is intentionally provider-neutral. It stores metadata and
references to secret material; it does not put secret values in repository rows.

```text
Repository
  ├─ backend_kind, endpoint/location, security posture policy, lifecycle state
  ├─ RepositoryCredential[]       (references only)
  ├─ RepositoryCapability[]       (declared/discovered/verified claims)
  └─ RepositoryVerification[]     (timestamped technical evidence)
```

### Repository

Represents one backend target, its canonical backend kind, endpoint/location,
and a desired security posture. It holds no password, access key, private key,
or backend token.

### RepositoryCredential

Represents an identity reference and its scope, never a plaintext secret.

Required purpose values:

| Purpose | Intended assignee | Baseline policy |
|---|---|---|
| `BACKUP_WRITE` | Normal backup agent | Required for backup; must not permit forget/prune/delete repository |
| `RESTORE_READ` | Restore worker or explicitly authorized restore agent | Read/restore only where backend can enforce it |
| `RETENTION` | Trusted retention runner | May run approved forget/prune; never distributed with `BACKUP_WRITE` |
| `REPOSITORY_ADMIN` | Repository custodian | Backend administration only; never delivered to agents |

Metadata required later: purpose, provider reference, backend principal ID,
credential state, created/rotated/expires/revoked timestamps, last verified
timestamp, and non-secret audit correlation ID. Secret values, password hashes
that are not needed for verification, and raw credentials remain outside this
record.

### RepositoryCapability

Each capability is an independently assessed claim:

`can_backup`, `can_restore`, `can_forget`, `can_prune`,
`can_delete_repository`, `append_only`, `immutable`.

Every claim has a provenance state:

| State | Meaning |
|---|---|
| `DECLARED` | Operator/UI supplied a desired or asserted value |
| `DISCOVERED` | OSB read backend configuration/metadata but has not performed a behavioral proof |
| `VERIFIED` | OSB performed an authenticated technical check with timestamped evidence and expected result |

Only `VERIFIED` may produce a green security status. Failure, stale evidence,
missing permission to inspect, or unsupported backend is not a green result.

### RepositoryVerification

An immutable evidence record: verification kind, capability, verifier version,
non-secret backend fingerprint, credential purpose used, result, observation
timestamp, expiry/staleness deadline, and sanitized failure code. It must never
store raw endpoint credentials, response bodies containing secrets, or command
lines with secret values.

## Credential lifecycle

```text
CREATE → DISTRIBUTE → USE → ROTATE → REVOKE → AUDIT
```

1. **CREATE:** a custodian creates a backend principal outside a normal agent.
   OSB stores a provider reference and public metadata, never the raw value in
   repository records.
2. **DISTRIBUTE:** prefer a short-lived, purpose-bound delivery to the agent at
   job start. If the backend cannot issue short-lived credentials, deliver only
   a durable `BACKUP_WRITE` identity to the agent's least-privileged local
   secret location.
3. **USE:** inject only for the running restic child process. No secret may be
   included in logs, API responses, UI state, audit details, errors, command
   strings, or progress payloads.
4. **ROTATE:** create a replacement, validate it with a non-destructive
   capability check, switch new work, then revoke the predecessor. Rotation is
   complete only after old credential denial is verified.
5. **REVOKE:** stop future issuance, invalidate/revoke backend identity, mark
   all affected agent assignments, and force re-acquisition before next job.
6. **AUDIT:** record identity/purpose/reference and outcome, never secret value.

### Availability constraints

- **Control-plane outage:** a short-lived credential cannot be refreshed. The
  policy must explicitly choose fail-closed (recommended for new managed
  identities) or a bounded, locally sealed emergency cache.
- **Agent restart:** no credential is recovered from logs or command history;
  it is reacquired from its provider or the controlled local secret store.
- **No Vault/KMS requirement in E2.1:** the abstraction must not force one.
  It must, however, avoid an API that assumes plain environment variables are a
  permanent secret-provider contract.

## Provider boundary (design only)

```go
// Conceptual boundary only — not E2.1 production code.
type SecretProvider interface {
    Resolve(ctx context.Context, ref SecretReference, purpose CredentialPurpose) (SecretLease, error)
    Revoke(ctx context.Context, ref SecretReference) error
}
```

The first implementation target should be an OSB encrypted local store with
OS-protected key material where available. Environment compatibility remains a
read-only legacy provider, not a source for new managed credentials. A later
Vault/KMS provider can implement the same reference-and-lease contract.

## Legacy transition

| State | Meaning | Security status |
|---|---|---|
| `LEGACY` | `RESTIC_REPO` / `RESTIC_PASSWORD` supplied by existing environment | Compatible, unverified, no separation claim |
| `MANAGED` | Purpose-bound credential reference and controlled delivery exist | Configured, subject to backend verification |
| `VERIFIED` | Backend capability and old-credential revocation have technical evidence | Eligible for green status per capability |

E2.1 introduces no breaking migration. Existing agents continue to run in
`LEGACY`; UI must show that state honestly rather than rendering green security
badges.

## Design decisions

1. **Separate encryption from backend identity.** A future credential assignment
   records both classes independently; neither implies the other.
2. **Purpose is explicit, not inferred from agent role.** A backend credential
   has exactly one security purpose in the OSB model.
3. **No agent-held retention/admin credential.** `RETENTION` and
   `REPOSITORY_ADMIN` require a separate trusted execution path.
4. **Verification is evidence-based and expiring.** `VERIFIED` becomes stale
   after a backend-specific interval or configuration change.
5. **Backend adapters own capability semantics.** The canonical model does not
   pretend local/NAS, rest-server and S3 enforce the same controls.
6. **Fail honestly.** Unsupported or inaccessible checks return `UNKNOWN` or
   `UNVERIFIED`, never a green inference.

## First implementable E2 slice

**E2.1a — Repository backend classification and declared posture.**

Implement only the safe metadata foundation: canonical backend kinds, legacy
state, purpose-bearing credential *references* (no secret values), and the
`DECLARED` / `DISCOVERED` / `VERIFIED` capability provenance. It enables honest
UI/API status without changing agent secret delivery. It must land with tests
that prove a declared field can never be returned as verified.

E2.1a is preferred before credential delivery because it establishes the data
contract needed by E2.2 while keeping the legacy mode operational.
