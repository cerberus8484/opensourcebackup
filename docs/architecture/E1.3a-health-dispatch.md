## Lokaler E2E-Beweis (12.08.2026)

**Setup (nur lokal/Test):** Wegwerf-PostgreSQL, echte `control-plane.exe` (127.0.0.1:18080, migriert selbst),
echte `agent.exe`, Fake-`restic` (loggt jede Invocation). **Architektur-Ehrlichkeit:** der reale Agent
heartbeatet am Poll-Anfang → er heilt sich auf ONLINE, *bevor* er je einen eigenen `system_offline`-Block
sähe. Die **Block-Entscheidungen (A/B/E/F/G/H)** werden daher über den **echten Agent-Auth-Endpoint**
`PUT /v1/agent/jobs/{id}/start` (echtes Bearer-Token) getriggert = realer server-seitiger Dispatch + realer
Guard; die **Recovery (C/D)** mit dem echten Agent-Binary. Der Deferred-Handling des Agents auf ein 429 ist
codeidentisch zum bereits in E1.2 E2E-bewiesenen Maintenance-Fall. Keine Secrets im Repo.

| Phase | Erwartung | Ergebnis |
|---|---|---|
| **A** ACTIVE+OFFLINE | 429 `system_offline`, pending, kein restic | HTTP 429 · `system_offline` · pending · restic=0 |
| **B** UNKNOWN (last_seen NULL) | 429 `system_health_unknown`, pending, kein restic | HTTP 429 · `system_health_unknown` · pending · restic=0 |
| **E** MAINTENANCE+OFFLINE | Priorität → `system_maintenance` | HTTP 429 · `system_maintenance` (nicht system_offline) |
| **H** MAINTENANCE+ONLINE | E1.2 → `system_maintenance`, kein Start | HTTP 429 · `system_maintenance` · pending |
| **F** ACTIVE+DEGRADED | erlaubt + Warning | HTTP 200 · running · CP-Log `job dispatched to degraded agent` (1×) |
| **G** ACTIVE+ONLINE+belegt | E1.1 → `agent_concurrency_limit` | HTTP 429 · `agent_concurrency_limit` · pending |
| **C/D** Recovery | offline→heartbeat→online→run→success | vor Agent 429 `system_offline`; nach Agent-Heartbeat `Health=online`, `OperationState=active` (unverändert), Job **success** |

**Prozess-Beweis:** In allen Block-Phasen `restic backup`-Invocations = **0**. Erst nach der Recovery
(echter Agent, ONLINE) laufen restic-Prozesse — alle Invocations tragen Zeitstempel *während* des
Agent-Laufs. Der echte Agent arbeitete nach Recovery **alle zuvor deferred pending Jobs** ab (kein
manuelles Reparieren) und brachte den Ziel-Job `000000cc` `pending→running→success`.

**Langläufer-Beweis (dokumentiert, kein Code):** Ein laufender synchroner Backup kann `last_seen` altern
lassen, **ohne** stale zu sein. Das Health-Gate wird **nur vor neuem Dispatch** angewendet — nie auf einen
bereits laufenden Job. Stale-Running bleibt Sache des **progress-/`started_at`-basierten Reapers**
(30min/12h), der einen langen, Progress meldenden Backup nicht killt. Kein neuer `last_seen`-Timeout eingeführt.

## Bestandsanalyse: reale Heartbeat-/Health-Architektur (FACT)
1. **`last_seen` wird nur beim Heartbeat aktualisiert** (`PUT /v1/agent/heartbeat → handleAgentHeartbeat →
   SystemStore.UpdateLastSeen`). Poll/Claim/Start schreiben `last_seen` nicht.
2/3. **Jeder Poll aktualisiert `last_seen`**, weil `Agent.poll()` **zuerst** `Heartbeat()` ruft, dann erst
   `ListPendingJobs` und `StartJob`.
4. Ein **aktiv pollender** Agent ist zum `StartJob`-Zeitpunkt praktisch immer ONLINE (Heartbeat lag ms davor)
   → **kein** OFFLINE-und-pollt-gleichzeitig; **kein Deadlock**.
5. **Ein langer synchroner Backup lässt `last_seen` altern** (kein Heartbeat währenddessen) → der lebende
   Agent erscheint DEGRADED/OFFLINE. Deshalb steuert Health **nicht** die Stale-Erkennung.
6. Verschwindet der Agent, failt der **progress-basierte Reaper** den `running` Job.
7. Reaper: alle 10min; `progressGrace=30min` (Progress-Stille), `startGrace=12h` (nie Progress),
   `pendingGrace=6h` (nie geclaimt). Nutzt `last_progress_at`/`started_at`, **nicht** `last_seen`.
8. Signale zur Unterscheidung „offline" vs. „langer Backup": `last_progress_at` (Agent meldet ~alle 2s),
   `started_at`, `last_seen` (bei langem Backup stale). Der Reaper nutzt bewusst Progress+Start.

## Gewählte Health-Semantik
Schwellen unverändert (begründet): `ONLINE ≤ 2min`, `DEGRADED ≤ 15min`, sonst `OFFLINE`; `UNKNOWN` = nie
gesehen. Bei Default-Poll 30s bleibt ein gesunder Agent mit Reserve ONLINE (übersteht mehrere verpasste
Polls). Ein Agent wird erst BLOCKED, wenn er >15min stumm ist (≈30 verpasste Polls = real weg) — und
erholt sich beim nächsten Heartbeat automatisch. Dispatch-Verhalten:
`ONLINE`→erlaubt · `DEGRADED`→erlaubt + **Warning-Log** · `OFFLINE`→BLOCKED `system_offline` ·
`UNKNOWN`→BLOCKED `system_health_unknown`. BLOCKED = kein Fehler, Job bleibt pending, kein restic, kein fail.

**Deadlock-Ausschluss (Regel 4):** Da `Heartbeat()` Schritt 1 jedes Polls ist (vor `StartJob`), gilt
`OFFLINE → Agent meldet sich (Heartbeat) → ONLINE → nächster Dispatch erlaubt`. Der verbotene Zustand
„OFFLINE → meldet sich → bleibt OFFLINE → Job blockiert für immer" ist konstruktiv ausgeschlossen und per
Test `offline→online re-enables pending job` bewiesen.

## Dispatch-Pfad vorher / nachher
**Vorher (E1.2):** `AdmitStart` = TX: Job `FOR UPDATE` → Operation-State-Gate → advisory lock →
Concurrency → `pending→running`.
**Nachher (E1.3a):** dieselbe TX; die Systems-Abfrage liest jetzt `operation_state, last_seen` in einem
Zug. Reihenfolge: Job `FOR UPDATE` → **Operation-State-Gate (zuerst, deterministische Priorität)** →
**Health-Gate (OFFLINE/UNKNOWN → BLOCKED)** → advisory lock → Concurrency → `pending→running`. E1.1/E1.2-
Logik unverändert; nur das Health-Gate ist zwischengeschaltet. Jede Decision trägt jetzt `HealthState` +
`LastSeenAgeSec` (Observability).

**Priorität (deterministisch):** `Operation State → Health → Resource`. Beispiel `MAINTENANCE + OFFLINE`
→ immer `system_maintenance` (bewiesen). `ACTIVE + OFFLINE` → `system_offline`.

## Stale-Running: Erkenntnisse & Aufschub (E1.3b)
Der bestehende Reaper ist bereits mehr-signalig (Progress + Start) und großzügig (30min/12h), sodass lange
Backups nicht fälschlich gekillt werden. `last_seen` als Stale-Signal würde bei langen synchronen Backups
false-positives erzeugen. Ein neuer Timeout wäre riskanter als der Status quo → **DEFERRED TO E1.3b**
(sauberes Multi-Signal-Design als eigener Slice). Kein „gefährlicher Timeout" erfunden.

## Observability
Block-Log `job dispatch blocked` mit `system/agent id`, `health_state`, `last_seen_age_sec`, `job id`,
`reason`. Zusätzlich Warning `job dispatched to degraded agent`. Keine Secrets.

## Bekannte Grenzen
- **Multi-Job-Poll-Batch:** Läuft in einem Poll ein langer erster (synchroner) Job, altert `last_seen`;
  ein *zweiter* Job desselben Batches könnte dann health-blockiert werden, bis der nächste Poll neu
  heartbeatet. **Selbstheilend** (nächster Poll), kein Datenverlust; zudem greift ohnehin der Concurrency-
  Guard, solange der erste Job läuft.
- Health ist Dispatch-Gate + im System-API sichtbar, aber **kein** Stale-Running-Signal (bewusst, s.o.).
- Kein Auto-DRAINING→MAINTENANCE, keine Health-Engine über die Ableitung hinaus.

## Regression-Risiken
Gering. `JobStore`-/`SystemStore`-Interfaces unverändert (nur `DispatchDecision` um additive Felder
erweitert). Fixture-Änderung (`last_seen=now`) betrifft nur Testdaten und macht Dispatch-Fixtures realistisch
ONLINE. Reihenfolge Operation→Health garantiert stabile Block-Reasons.
