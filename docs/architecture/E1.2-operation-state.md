## Lokaler E2E-Beweis (12.08.2026)

**Setup (nur lokal/Test):** Wegwerf-PostgreSQL (Docker), echte `control-plane.exe` (dev-mode,
127.0.0.1:18080, migriert selbst inkl. 000024) und echte `agent.exe`; Fake-`restic` (loggt jede
Invocation → Prozess-Beweis). State-Wechsel über `PUT /v1/systems/{id}/operation-state` mit
CSRF-Double-Submit-Handshake und RBAC (dev-mode = synthetischer Admin ≥ operator). Keine Secrets im Repo.

Beteiligte IDs: Agent/System `1111…1111`, Offline-System `2222…0002`, Job J1 `4444…4444`,
laufender Job `6666…6666`, Job J2 `5555…5555`.

**A — Maintenance Block:** `PUT …/operation-state {state:maintenance}` → HTTP **200**, DB `operation_state=maintenance`.
Agent startet, pollt J1: J1 bleibt **pending**, `restic backup`-Invocations = **0**, CP-Log
`reason=system_maintenance`, Agent-Log **deferred** (4×). `GET system` → `OperationState=maintenance`,
`HealthState=online` → **MAINTENANCE + ONLINE**.

**B — State Transition (echter API-Pfad):** `PUT {state:active}` → HTTP **200**, DB `operation_state=active`.
Audit-Log (`system.operation_state_changed`), Actor `dev-admin`:
`old=active new=maintenance reason=e2e maintenance window` und `old=maintenance new=active reason=maintenance done`.

**C/D — Retry + Result:** nächster Poll admittet J1 → `job started` → **`restic backup`-Invocations = 1**
→ `job completed snapshot_id=246f5ac8…` → J1 **success** über den normalen Snapshot-/Result-Pfad.

**E1.1 Regression:** unter `active` mit einem laufenden Job → zweiter Job (J2) `pending`, CP-Log
`reason=agent_concurrency_limit`, `restic backup`-Invocations bleiben **1** (kein zweiter Backup-Prozess).

**E — Independence:** Offline-System (`last_seen` 30 min alt) → `GET` liefert `OperationState=active`,
`HealthState=offline` → **ACTIVE + OFFLINE**. `PUT operation-state` auf diesem System ließ `last_seen`
**unverändert** (vorher = nachher) → Operation-State und Health-Signal sind unabhängig; keine Health-Engine.

**Invocation-Log (Prozess-Beweis):** genau ein `backup` (J1), erst **nach** der Aktivierung
(`unlock`/`init`/`backup` mit Zeitstempel nach dem `→active`), nie während Maintenance, nie für J2.

## Die zwei getrennten Dimensionen
```
OPERATION STATE (gespeichert, admin-gesetzt)     HEALTH STATE (abgeleitet, beobachtet)
─────────────────────────────────────────       ────────────────────────────────────
active     → neue Jobs erlaubt                    online    (last_seen ≤ 2min)
maintenance→ keine neuen Jobs                     degraded  (≤ 15min)
draining   → keine neuen Jobs, laufende fertig    offline   (> 15min)
suspended  → keine neuen Jobs                     unknown   (nie gesehen)
```
Ein System kann jede Kombination haben (z.B. `MAINTENANCE + ONLINE`, `ACTIVE + OFFLINE`). Operation
State steuert Dispatch; Health sagt nur, ob der Agent erreichbar ist. `OFFLINE` ist **kein**
Operation State. Sie beeinflussen sich nicht: Health wird rein aus `last_seen` berechnet (nie
gespeichert); ein Operation-State-Wechsel fasst `last_seen` nicht an (Test 12).

## Migration / Datenmodell
`ALTER TABLE systems ADD COLUMN operation_state TEXT NOT NULL DEFAULT 'active'
CHECK (operation_state IN ('active','maintenance','draining','suspended')),
ADD COLUMN operation_state_changed_at TIMESTAMPTZ;` — **rückwärtskompatibel** (Bestandsrows → `active`).
Actor wird **nicht** am System gespeichert (kein `operation_state_changed_by`) — er lebt im
append-only Audit-Log. Nur `operation_state_changed_at` bleibt am System (für Anzeige).

## API
- `PUT /v1/systems/{id}/operation-state` — Body `{ "state": "...", "reason": "..." }`, RBAC `operator+`.
  400 bei ungültigem State, 404 bei unbekanntem System. Antwort: aktualisiertes System inkl. Health.
- `GET /v1/systems` und `GET /v1/systems/{id}` liefern jetzt zusätzlich `OperationState` (gespeichert)
  und `HealthState` (abgeleitet) — additiv, bestehende Felder unverändert.

## Audit
Bei jeder Änderung: `system.operation_state_changed`, `ResourceSystem`, Actor = Session-E-Mail
(Dev-Mode: `dev-admin`), `Details="old=<x> new=<y> reason=<z>"`, gehashter IP, Severity info.
Reason wird bereinigt (einzeilig, gekappt).

## Dispatch-Pfad vorher / nachher
**Vorher (E1.1):** `AdmitStart` = TX: Job-Row `FOR UPDATE` → advisory lock/System → Concurrency-Count
→ `pending→running`.
**Nachher (E1.2):** dieselbe TX, ein Schritt **davor** eingefügt: Job-Row `FOR UPDATE` →
**Operation-State-Read; wenn ≠ active → BLOCKED (`system_maintenance|draining|suspended`), Job bleibt
pending** → advisory lock → Concurrency-Count → `pending→running`. Reihenfolge damit
`Policy → Operation State → (Health-Platzhalter) → Resource Guard → Dispatch`. E1.1-Concurrency-Logik
unverändert; das Gate ist nur vorgeschaltet.

## Bekannte Grenzen
- **Manuelle Jobs:** Es gibt heute **keinen** getrennten manuellen Dispatch-Pfad — jeder Job-Start läuft
  über `agent StartJob → Guard`. MAINTENANCE blockiert daher *alle* neuen Dispatches (automatisch **und**
  manuell). Das entspricht der Vorgabe „keine Sonderlogik erfinden, nur um manuelle Jobs zu erlauben".
- **Health** ist abgeleitet + im API sichtbar, aber (noch) **kein** Dispatch-Gate — der „Agent Health"-
  Schritt der Zielkette ist Platzhalter für einen späteren Slice.
- **Kein** Auto-`DRAINING→MAINTENANCE` (bewusst = E1.2b). DRAINING bedeutet in E1.2 nur: keine neuen
  Jobs, laufende dürfen fertigwerden. SUSPENDED beendet laufende Jobs **nicht** automatisch.
- RBAC: `operator+` darf alle vier States setzen (inkl. suspend). Feinere Governance (Vier-Augen,
  admin-only suspend) ist ein späterer Slice.

## Regression-Risiken
Gering. `JobStore`-Interface unverändert; `SystemStore` +1 Methode (Stub mitgezogen). Migration additiv
+ rückwärtskompatibel. Neue Route additiv. `GET /v1/systems*` liefert ein zusätzliches Feld
(`HealthState`) via Embedding — alle bestehenden Felder unverändert. Block-Log-Text von E1.1 wurde von
`"job dispatch blocked: agent concurrency limit"` zu generisch `"job dispatch blocked"` (+ `reason`)
geändert; der stabile maschinenlesbare Teil (`reason=agent_concurrency_limit`) bleibt.
