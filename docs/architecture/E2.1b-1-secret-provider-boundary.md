# E2.1b-1 — SecretProvider Boundary & Authorized Reference Resolution

> Status: IMPLEMENTED / TESTED. E2E VERIFIED: NO. PRODUCTION VERIFIED: NO.

## Scope

E2.1b-1 creates a server-side authorization boundary for future repository
secret resolution. It deliberately does **not** add an HTTP route, agent
request, secret delivery, provider implementation, Vault/KMS integration,
migration, rotation, lease, TTL, or replacement for `RESTIC_PASSWORD`.

The `internal/secrets` package declares a `SecretProvider` interface but does
not invoke it. It returns repository credential-reference **metadata** only;
no secret value is resolved, persisted, logged, serialized, or delivered.

## Trust boundary

The only inputs to `AuthorizedReferenceResolver.ResolveForAgent` are trusted
server-side IDs:

```text
authenticated system ID + job ID
          |
          v
job -> policy -> repository -> job-type purpose -> active reference
```

The caller cannot supply a repository ID, credential purpose, provider type or
provider reference. A job belonging to another system fails with an
authorization error before policy, repository or credential-reference metadata
is read.

## Purpose mapping

| Job type | Derived purpose | Notes |
|---|---|---|
| `backup` | `BACKUP_WRITE` | The only normal backup-job mapping. |
| `verify` | `RESTORE_READ` | `verify` is legacy string technical debt; its mapping is centralized in one function. |
| `retention` | `RETENTION` | Canonical mapping only; no agent delivery path exists. |
| any other type | denied | `REPOSITORY_ADMIN` is never derived for an agent job. |

## Reference-state and error model

Only an `ACTIVE` reference for the derived purpose can be returned. Missing,
disabled, revoked, unsupported and ambiguous states fail closed. Lookup errors
are represented by internal sentinel errors for job, policy and repository
stages. A future HTTP handler must map authorization failures to a generic
external response and must not expose provider or reference details.

The E2.1a database constraint permits one reference per repository and purpose.
The resolver additionally rejects duplicate matching references defensively.

## Legacy fallback rule

`LegacyFallbackPermitted` documents the future compatibility policy without
changing the current agent configuration: if any reference exists for a
purpose, its state governs that purpose. In particular, a disabled or revoked
managed reference must never fall back to `RESTIC_PASSWORD`. Legacy fallback is
only permissible when no reference exists for that purpose.

## Tests

Unit tests prove:

- a system may resolve only its own job;
- backup jobs select `BACKUP_WRITE`, never restore, retention or admin refs;
- verify and retention use their own canonical mappings;
- missing job/policy/repository/reference paths are controlled failures;
- disabled, revoked and ambiguous references fail closed; and
- the legacy-fallback policy denies fallback whenever a purpose has a managed
  reference.

## Deferred scope

E2.1b-2 may add a single external provider implementation and a separate,
agent-only runtime-delivery design. It must resolve values only after this
authorization boundary succeeds, over verified TLS, and keep them only for the
restic child-process lifetime.
