## Bestandsanalyse (10 Fragen)
1. Repo je Job: **INFERENCE/GAP** — kein direktes `backup_jobs.repository_id`; abgeleitet über
   `policy_id → backup_policies.repository_id` (nullable).
2. Am Dispatch bestimmbar: **FACT** — via JOIN, außer `repository_id IS NULL`.
3. Speicherung: **FACT** — `backup_policies.repository_id` (Migration 6); Jobs haben keins.
4. Jobs ohne Repo: **FACT/GAP** — möglich; Agent failt sie; Repo-Gate wird übersprungen.
5. Mehrere Agents/Repo: **FACT** — zentrales rest-server-Repo real geteilt.
6. Repo-Capacity: **FACT/GAP** — `RepositoryHealth` on-demand, keine gespeicherte Capacity (out of scope).
7. Naht: **FACT** — bestehende `AdmitStart`-TX.
8. Mehrere CP-Instanzen: **INFERENCE** — möglich; Advisory-Locks wirken Postgres-weit.
9. Advisory-Lock wiederverwendbar: **FACT** — `pg_advisory_xact_lock`; hier ein fester globaler Key.
10. Teure Queries: **INFERENCE** — Counts filtern `status='running'` (durch Global-Limit ≤20 beschränkt)
    → billig. Einziger Skalen-Punkt: der globale Entscheidungs-Lock.

## Neue Guard-Reihenfolge
```
Policy → Operation State → Health State → Global → Repository → Agent → Dispatch
```
Deterministische Block-Reason-Priorität: `system_maintenance/draining/suspended` → `system_offline/
system_health_unknown` → `global_concurrency_limit` → `repository_concurrency_limit` →
`agent_concurrency_limit`. Alles in **einer** Transaktion; E1.1/E1.2/E1.3a-Logik unverändert, die
Resource-Gates sind nur erweitert (global + repo vor agent).

## Locks & Transaktionen
- **Lock-Key:** ein fester `globalDispatchLockKey` (bigint-Konstante).
- **Scope:** die gesamte Resource-Entscheidung (Global-/Repo-/Agent-Count + `pending→running`).
- **Reihenfolge:** **ein einziger** Lock → per Definition deadlockfrei (keine Lock-Ordering-Frage).
- **Transaktionsgrenze:** `pg_advisory_xact_lock` wird nach den Operation-/Health-Gates genommen und mit
  `COMMIT`/`ROLLBACK` automatisch freigegeben — gehalten nur für die (ms-schnelle) Entscheidung, **nie**
  während eines Backups.
- **Bewusste Entscheidung:** Der E1.1-per-Agent-Lock wird durch den globalen Entscheidungs-Lock ersetzt/
  subsumiert (die Agent-Invariante bleibt erhalten, da der globale Lock alle Entscheidungen serialisiert).
  Ein globaler Lock serialisiert Dispatch-**Entscheidungen** plattformweit; bei aktueller Skala (ms-
  Entscheidungen, dutzende Agents) unkritisch. Per-Repository-Locks für mehr Entscheidungs-Parallelität
  sind eine spätere Optimierung (RISK nur bei sehr hoher Dispatch-Rate).

## Limits & Konfiguration
Konservative Server-Defaults (keine Migration): **Global 20 · Repository 5 · Agent 1**. In
`catalog.DefaultDispatchLimits()`; via `NewDispatchGuardWithLimits` injizierbar. `main.go` verdrahtet die
Defaults und loggt sie beim Start. Konfigurierbarkeit pro Repo/Policy ist ein späterer Slice.

## Backpressure
Kein neues Queue-/Broker-System. BLOCKED = kein Fehler, Job bleibt `pending`, kein restic, kein `failed`,
Retry beim nächsten Agent-Poll (Default 30s) bzw. Scheduler-Zyklus. **Kein Busy-Loop:** die Retry-Kadenz
ist durch das Poll-Intervall (30s) begrenzt; der Block-Log ist INFO, ~1×/Poll/Job → keine Log-Flut. Es
wurde bewusst **keine** Retry-/Backoff-Engine eingeführt, da die bestehende Poll-Kadenz die Backpressure
bereits sauber liefert.

## Fairness
FIFO **pro Agent** (`ListPendingBySystemID ORDER BY created_at ASC`). Die Zuteilung freier Global-/Repo-
Slots ist **opportunistisch** (der zuerst pollende Agent nach Slot-Freigabe gewinnt) — keine gewichtete
Fair-Queue. **Starvation-Risiko (dokumentiert):** ein langsam pollender Agent könnte an einem geteilten
Repo/Global-Slot von schnell pollenden Agents verdrängt werden. Kein trivialer Fix ohne Priority-Queue →
bewusst **nicht** in E1.4 gebaut.

## Observability
Block-Log `job dispatch blocked` mit `job_id`, `agent_id`, `repository_id`, `global_running/limit`,
`repository_running/limit`, `agent_running/limit`, `health_state`, `reason`. Keine Secrets. Die 429-Response
trägt dieselben Zähler. **Metrics-Namen vorbereitet** (`dispatch_blocked_global_total`,
`dispatch_blocked_repository_total`, `dispatch_blocked_agent_total`) — noch nicht als Counter verdrahtet, da
das bestehende Metrics-System scrape-/store-basiert ist (Event-Counter = eigener kleiner Folgeschritt).

## Tests
Global (unter/am/frei) · Repository (am Limit blockt, anderes Repo parallel) · Priorität global>repo>agent ·
Priorität repo>agent · Kombination Global10/RepoA2/Agent1 · Operation-State & Health vor Resource-Gates ·
**Race: global 5/5**, **Race: repository 3/3**, **Race: agent 1/1 (E1.1-Regression)**. Plus unveränderte
E1.2/E1.3/Reaper/State-Machine/Outbox/RBAC-Suiten grün.

## Race-Evidence (DB als Source of Truth)
- Global: 20 gleichzeitige Dispatches, `Global=5` → genau 5 `Allowed`, `count(running)=5`.
- Repository: 10 gleichzeitige Dispatches auf dasselbe Repo, `PerRepository=3` → 3 `Allowed`,
  `count(running on repo)=3`.
- Agent: 10 gleichzeitige Dispatches auf denselben Agent, `PerAgent=1` → 1 `Allowed`,
  `count(running per agent)=1`.

## Bekannte Grenzen
- Ein globaler Entscheidungs-Lock serialisiert Dispatch-Entscheidungen (per-Repo-Lock = spätere Optimierung).
- Repo-Gate übersprungen, wenn die Policy kein Repository hat (der Agent failt solche Jobs ohnehin).
- Keine Capacity-basierte Backpressure (keine gespeicherte Repo-Capacity).
- Limits sind Server-Konstanten (noch keine per-Repo/Policy-Konfiguration).
- Opportunistische Slot-Zuteilung (Starvation-Risiko, s. Fairness).

## Regression-Risiken
Gering. `JobStore`/`SystemStore`-Interfaces unverändert; `DispatchDecision` nur additiv erweitert.
`NewDispatchGuard(db, maxPerAgent)` bleibt (Default-Global/Repo) → bestehende Aufrufer/Tests unverändert.
Der E1.1-per-Agent-Lock wurde durch den globalen Lock ersetzt — Agent-Invariante bleibt bewiesen (Race-Test).

### Invarianten (während der Blockphasen erfasst, nicht nur am Ende)
Mid-Window-Snapshots zeigten die Zähler **exakt am Limit, nie darüber**; die restic-Invocation-Timestamps
belegen: max. 2 Backups global gleichzeitig, nie 2 auf einem Repo, nie 2 auf einem Agent.
`global_running ≤ 2`, `repository_running ≤ 1`, `agent_running ≤ 1` galten durchgängig.

### Backpressure
BLOCKED = HTTP 429 → Job bleibt `pending`, **kein** `failed`, **kein** Ersatzjob, **kein** Busy-Loop
(Retry-Kadenz = Poll-Intervall **2 s**). Slot-Freigabe genügt: der nächste reguläre Poll startet den Job
(A/B: agentB; D/E: agentC). Keine neue Retry-Engine.

### Restic-Prozess-Evidence
Jede fake-restic-Invocation protokolliert Timestamp + PID + Subcommand + Args. Belegt eindeutig, wie viele
echte Backup-Prozesse gleichzeitig liefen: A=1 (Blockphase), B=2 sequentiell, C=2 parallel (verschiedene
Repos), D/E=2 gleichzeitig + 1 nach Release.

### Regressions-Bestätigung
Nach dem Gate: `gofmt` sauber, `go vet ./cmd/control-plane` sauber, `go build ./...` ok, E1.4-Integrations-
suite gegen den Wegwerf-Container erneut grün (`ok internal/catalog 7.124s`).

### Bekannte Grenzen des Gates
- Kein echtes restic/Repository (fake-restic-Stub), kein Deployment, keine Multi-Instanz-CP.
- F/G/H nutzen SQL-fixierte running-Slots als Fixtures (ein running-Job zählt unabhängig von seiner
  Herkunft) — die getestete Codepfad-Entscheidung (`AdmitStart` über den realen HTTP-Endpunkt) ist real.
- Single-threaded Agent: ein einzelner Agent sendet nie zwei gleichzeitige StartJobs; die Agent-Grenze ist
  server-seitige Defense-in-Depth (deshalb F über den Endpunkt bewiesen).
