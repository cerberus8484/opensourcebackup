## Lokaler E2E-Beweis (12.08.2026)

**Setup (nur lokal/Test):** Wegwerf-PostgreSQL (Docker, Port 55432, wird bei jedem Lauf neu
migriert), echte `control-plane.exe` (dev-mode, Port 127.0.0.1:18080) und echte `agent.exe`.
Zwei Agent-Prozesse mit demselben Token = zwei gleichzeitige Dispatcher (genau der Fall, den der
Guard schützt — ein einzelner Agent führt Jobs synchron aus und käme nie in den 429-Pfad).
Fake-`restic` (deterministisch, hält den Slot per `FAKE_RESTIC_SLEEP`, loggt jede Invocation) →
Prozess-Zählung als Beweis. Keine Secrets/Tokens im Repo (nur im lokalen Scratchpad).

Beteiligte IDs: Agent/System `1111…1111`, Job J1 `4444…4444`, Job J2 `5555…5555`.

**A — Concurrency Block** (J1 läuft, J2 wird versucht):
- DB: `J1 = running`, `J2 = pending`. `backup`-Invocations = **1** (kein zweiter restic-Prozess).
- CP-Log: `job dispatch blocked: agent concurrency limit … running_jobs=1, limit=1, reason=agent_concurrency_limit` (HTTP 429).
- Agent-Log: `dispatch deferred — agent at concurrency limit; job stays pending` (4× über die Poll-Zyklen, Job blieb pending, **kein** `failed`).

**B/C — Slot Release → Retry → Result** (J1 abgeschlossen):
- `job completed job_id=4444… snapshot_id=a45a559e… ` → `J1 = success`.
- 0,02 s später: `job started job_id=5555…` → J2 `pending→running` (Guard erlaubt, Slot frei).
- `backup`-Invocations = **2** (J2 lief real, nie 3 → nie Doppelstart).
- `job completed job_id=5555… snapshot_id=854dc1e0…` → `J2 = success` über den normalen
  Result-/Snapshot-Pfad.

**D — Evidence (Fake-`restic`-Invocation-Log, Prozess-Beweis):**
```
… sub=unlock  args="-r /tmp/e2e-repo unlock"                    # J1
… sub=init    args="-r /tmp/e2e-repo init --quiet"              # J1
… pid=40036 sub=backup args="… backup --json e2e-data …"       # J1  (schläft 12s, hält Slot)
… sub=unlock  …                                                 # J2  — erst NACH Slot-Freigabe
… sub=init    …                                                 # J2
… pid=31332 sub=backup args="… backup --json e2e-data …"       # J2  → success
```
Während J1 lief, existierte **nur** die J1-`backup`-Invocation (pid 40036) — der zweite
`backup`-Prozess (pid 31332) erscheint erst nach `J1 = success`. Damit ist bewiesen: beim
BLOCKED-Versuch startete **kein** zweiter restic-Prozess; der spätere Retry startete restic real.

## DB-/Migration-Änderungen
**Keine.** Bewusst keine Migration: Limit `1` ist ein zentraler Server-Default. Konfigurierbare
Limits (pro Agent/Repo/Global/Site) sind ein eigener späterer Slice. Der Guard nutzt eine
`pg_advisory_xact_lock` — keine Schemaänderung nötig.

## Dispatch-Pfad — vorher / nachher
**Vorher:** Agent pollt pending Jobs → `PUT /v1/agent/jobs/{id}/start` → `jobs.StartJob`
(`UPDATE ... status='running' WHERE status='pending'`) → restic. Keine Concurrency-Kontrolle:
mehrere pending Jobs desselben Agents konnten alle sofort auf `running` gehen.

**Nachher:** … → `startAgentJob` → **`DispatchGuard.AdmitStart`** (atomare TX):
`SELECT … FOR UPDATE` (Job-Row) → `pg_advisory_xact_lock(hash(system_id))` → `count(running for system)`
→ wenn `< limit`: `pending→running` + commit (**ALLOWED**); sonst commit ohne Änderung (**BLOCKED**,
Job bleibt pending, 429). Die State-Machine-Kanten sind unverändert; der Guard ist die neue,
komponierbare Vorstufe (Naht für spätere System-State-/Repo-/Global-/Site-Limits).

`running→running` gibt es nicht; **nur `running` belegt einen Slot.** Ein Job mit gesetztem
`cancel_requested_at` bleibt `running` → belegt den Slot korrekt weiter, bis der Agent `cancelled`
bestätigt.

## Race-Condition-Schutz
DB ist Source of Truth. Zwei Ebenen in einer Transaktion:
1. `FOR UPDATE` auf die Job-Row → kein Doppel-Dispatch desselben Jobs.
2. `pg_advisory_xact_lock` gehasht auf `system_id` → serialisiert Dispatch-Entscheidungen **pro Agent**;
   unterschiedliche Agents hashen auf verschiedene Keys und blockieren sich nicht. Count-Check +
   `pending→running` liegen unter demselben Lock → keine zwei Dispatcher können denselben Slot vergeben,
   auch über mehrere Control-Plane-Instanzen hinweg. Kein Redis/Kafka/K8s, keine In-Memory-Sonderlogik.

## Tests (alle grün)
1 kein laufender Job → allowed · 2 ein laufender → zweiter pending · 3 success → nächster darf ·
4 failed → nächster darf · 5 cancelled → nächster darf · 6 **paralleler Dispatch bleibt bei 1** ·
7 verschiedene Agents parallel · + unknown→NotFound, non-pending→IllegalTransition (ERROR≠BLOCKED).
Bestehende State-Machine- (8) und Outbox-Tests (9) unverändert grün.

## Beobachtbarkeit
Strukturiertes Log bei Blockade: `job dispatch blocked: agent concurrency limit`
mit `job_id`, `agent_id`, `running_jobs`, `limit`, `reason`. Keine Secrets. 429-Response trägt
denselben strukturierten `reason` (`agent_concurrency_limit`) für Cockpit/Client.
**Offen (bewusst, nächster kleiner Schritt):** Prometheus-Counter (das Metrics-Paket ist scrape-/
store-basiert; ein Event-Counter ist eigenes, kleines Plumbing).

## Bekannte Grenzen
- Nur **Per-Agent**-Limit, fix `1`. Global/Repo/Site/Policy-Limits sind Architektur-vorbereitet
  (Naht `DispatchAdmitter` + `DispatchDecision`), aber nicht implementiert.
- Guard greift nur, wenn via `WithDispatchGuard` verdrahtet (Produktion: ja). Ohne Guard →
  Fallback auf ungeschützten `StartJob` (nur relevant für Unit-Tests / Alt-Konstruktion).
- `-race` nicht gefahren (Windows ohne cgo/C-Compiler); für diesen Guard unkritisch, da der
  geteilte Zustand die DB ist, nicht Go-Speicher — die Invariante ist per DB-Count-Assertion belegt.

## Regression-Risiken
- Gering. `JobStore`-Interface **unverändert** → keine Stub-/Mock-Brüche.
- 429 ist ein neuer Statuscode auf `/v1/agent/jobs/{id}/start`; Client mappt ihn auf
  `ErrDispatchDeferred`, Agent behandelt ihn als „deferred". Ältere Agents (ohne dieses Mapping)
  würden 429 als generischen Fehler sehen → Job bliebe trotzdem pending (kein Datenverlust,
  nur ein Error-Log statt Info-Log). Sicher.

## Nächster sinnvoller Slice
**E1.2 — System Operation State**, mit **zwei getrennten Dimensionen** (nicht in einer Enum):
Operation State (`ACTIVE / MAINTENANCE / DRAINING / SUSPENDED`) = admin-gesetzt · Health State
(`ONLINE / DEGRADED / OFFLINE / UNKNOWN`) = beobachtet (aus Heartbeat). Ein System kann z.B.
`MAINTENANCE + ONLINE` oder `ACTIVE + OFFLINE` sein. Klinkt sich als Vorstufe **vor** den
Concurrency-Guard in dieselbe Dispatch-Naht.
